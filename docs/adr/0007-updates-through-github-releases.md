# ADR 0007 — Releases and in-app updates through GitHub Releases

- **Status:** Accepted
- **Date:** 2026-10-28

## Context

Players download TheLibrary as a Windows installer, and must be able to move to a newer version without uninstalling it. The owner wants:

- the app to tell the player at startup when a newer version is out, with its summary in the language of the app;
- the player alone to decide whether and when to install it — an update is never forced, and the app never checks again during a session;
- shipping a version to be a short routine, reviewed by the owner before anything reaches the players.

The project has no server of its own, and the first public versions are not signed with an Authenticode certificate yet.

## Decision

- **Releases are built only by GitHub Actions** (`.github/workflows/release.yml`), from a tag `vX.Y.Z` pushed by the owner after `pnpm release:prepare X.Y.Z`. The tag must point at a commit of `main`. The workflow has two jobs: the first runs every check of CI again and builds the NSIS installer (per-user, no administrator rights) with the signing key, a read-only token and no cache; the second, which runs no code of the project, creates the **draft** release with a write token. No job holds both the key and the write token. The owner tries the installer from the draft, then publishes it.
- **The installed app updates itself through the official Tauri updater plugin.** At startup it downloads `latest.json` from `https://github.com/GONZALEZeDev/TheLibrary/releases/latest/download/latest.json`, which GitHub serves from the latest published, non-pre-release release. A failed check is only logged. A newer version opens a dialog with the versions, the date and the summary; "Install now" downloads the installer, the plugin refuses it unless its signature matches the public key built into the app (`plugins.updater.pubkey` of `tauri.conf.json`) and was made for the version announced (`requireSignedVersion`: `latest.json` itself is not signed, so this stops an older genuine installer from being offered as a newer version), runs it in passive mode and the installer restarts the app. Settings → About can check again on demand.
- **Signing key custody.** The updater key pair was generated by the owner. The private key and its password exist only on the owner's machine (with a backup) and in the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, which reach only the build step of the release workflow. The public key is in `tauri.conf.json`, pinned by a test of the shell together with the endpoint.
- **Summaries in two languages.** `CHANGELOG.md` and `CHANGELOG.fr.md` have a section per version. The workflow puts both into the `notes` field of `latest.json` as `{"en": …, "fr": …}` and fails without the English one.
- **Least privilege.** The webview may check and install the update it found (`updater:allow-check`, `updater:allow-download-and-install`) and open the GitHub pages of the releases; it can give the updater no other address or key. A development build of the desktop app has no update gateway at all, so it never offers the public releases as updates of itself.
- **No third-party release action.** The Tauri CLI writes the installer and its signature; a script of the repository writes `latest.json`; the GitHub CLI creates the draft. One supply-chain dependency fewer.

## Consequences

- Losing the private key means the installed apps can never be updated again (they trust that key only): the players would have to reinstall by hand. The owner keeps a backup.
- A beta must be published as a normal release, never ticked "pre-release", or the installed apps never see it.
- Every start of the app contacts GitHub, which sees the player's IP address (documented in `PRIVACY.md`).
- Until the installer is signed with an Authenticode certificate (SignPath Foundation, once the project has a public release), Windows SmartScreen warns about an unknown publisher at the first install. Updates are not affected: their integrity is checked by the updater signature.

## Alternatives considered

- **Checking during the session or installing silently** — rejected by the owner: updates belong to the player.
- **`tauri-action`** to build and publish — rejected: a third-party action holding the signing secrets and a write token, for what the CLIs already do.
- **A static update server of the project** — rejected: GitHub Releases already hosts the files, with no server to run.
