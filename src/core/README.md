# `src/core` — domain model and pure logic

Everything here is **pure TypeScript**: no React, no Tauri, no network, no storage, no clock, no randomness. Functions take data and return data, which makes them trivial to test and safe to run anywhere (UI thread, Web Worker, tests).

## Rules

- May import other `core/` modules and `zod` only (enforced by ESLint).
- Side effects belong to `ports/` (interfaces) and `adapters/` (implementations).
- Throw `AppError` (`errors/app-error.ts`) with the right `kind` for expected failures.
- Every exported symbol has TSDoc; every non-obvious rule links to its source (ADR, API documentation).

## The match breakdown

The damage and build tab and the players tab of the match page, and the match list, rest on these modules. The archive readers and the breakdown work from the archive of a match or from the values the projection stored; the others name what they show: the type of a match from its row of the history, a rank from its badge, and the catalogues from their downloads. None of them downloads anything: the catalogues are given to them.

| Module                          | Role                                                                                                                                                                             |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `domain/match-type.ts`          | Reads the game mode and the match mode of a match as one type: normal, ranked, Street Brawl or custom                                                                            |
| `domain/rank.ts`                | The rank badges: their bounds, the tier names, and the splitting and naming of a badge (`Sentinel 4`)                                                                            |
| `domain/hero.ts`                | The heroes of the catalogue: their portrait and their loadout (weapon, melee attack and signature abilities by class name), which tell a hero's own damage sources from the rest |
| `deadlock-api/assets.schema.ts` | Reads the item and rank catalogues down to the few fields the app shows; keeps an image link only when it points to the asset bucket, the one origin the release CSP allows      |
| `match-detail/tracked-items.ts` | The tracked player's items in an archive (shop purchases, ability unlocks and upgrades) and the build they ended the match with                                                  |
| `match-detail/scoreboard.ts`    | The twelve players of an archive with their heroes, figures and ranks, Valve's top three, and the places the tracked player takes among them; never an account id                |
| `analysis/damage-matrix.ts`     | Reads the tracked player's damage to enemy heroes, by source, from the damage matrix of an archive (critical hits merged into their source, category rows left out)              |
| `analysis/damage-sources.ts`    | The damage values the projection stores for a match (`damage_source.`, `item_owned_damage.` and `ability_unlocked_at.` keys), with the damage dealt while a shop item was owned  |
| `analysis/damage-breakdown.ts`  | Builds the lines of the damage tab from the stored values of the match and of the earlier ones: shares, kinds, habits, and whether a source is used more or less than usual      |

## The review

The review page sums up the player's last 20 analysed matches, compared with the players of the tier above their rank and with the 20 matches before. These modules are pure: the projection reads the archive once and stores the values of each match, the review works from those values and from the community data it is given, and none of them downloads anything. The first six are new, the rest are what the review changed in older modules.

| Module                                | Role                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `match-detail/tracked-deaths.ts`      | The deaths of the tracked player in an archive, sorted, whoever or whatever killed them: `readTrackedDeathTimes` reads when they died, `readTrackedDeaths` also where, the slot of the killer and how long they took to kill; unknown (`null`, never fewer deaths) when the death details are missing or incomplete                                     |
| `deadlock-api/item-stats.schema.ts`   | Reads the item statistics of `GET /v1/analytics/item-stats` (`bucket=game_time_min`) down to the item, the minute and the number of purchases: when the players of a cohort buy each item; a row it cannot read is skipped, and only a body that is no list is an error                                                                                 |
| `analysis/review/review-values.ts`    | The review values the projection stores for a match: the deaths of each phase (and over the stretch the community data covers), the second each shop item was first bought and the deaths before that, the player's place on each figure of the scoreboard and in Valve's top three; a value that is not known is not written, never `0`                |
| `analysis/review/resistance-items.ts` | The fixed list of the twelve resistance items, by class name, which the item catalogue cannot give; the catalogue only names them                                                                                                                                                                                                                       |
| `analysis/review/review-rules.ts`     | The rules every row applies: when a match is weak or strong for a point (a percentile, a place, Valve's top three, the deaths before the first resistance item, the lane gap), where a buy minute stands among the purchases of a tier, the progress against the matches before, and the side of the summary a point is listed on                       |
| `analysis/review/damage-review.ts`    | The share of the damage each source dealt over a window of matches, pooled, and over the window before it, classified as the damage tab of the match page does                                                                                                                                                                                          |
| `analysis/cohort.ts`                  | Besides the cohort of a match, the cohort of the review: the tier above the player's own (`reviewCohortRank`: their own tier when it is the highest, every rank when they have none), how that choice is worded (`reviewComparedWith`), and `ANY_LENGTH_WINDOW`, the window that holds matches of every length, which the item statistics are asked for |
| `analysis/references.ts`              | `differenceOf` writes the difference between a figure and the one it is compared with (a share or an amount) once, for the comparison with the habits and with a tier                                                                                                                                                                                   |
| `analysis/phases.ts`                  | `spanOf` finds a phase among the ones a match reached                                                                                                                                                                                                                                                                                                   |
| `analysis/registry.ts`                | `PROJECTION_VERSION` is 4, since the review values (and, from version 4, the avoidable deaths) are stored with the metrics; `COMMUNITY_WINDOW_SUFFIX` ends the key of a value counted on the stretch the community curve covers (a metric's, and the deaths of a phase)                                                                                 |
| `deadlock-api/budgets.ts`             | The community analytics requests get 30 a minute (`ANALYTICS_RATE_LIMIT`): opening the review asks for a cohort of each duration window of the last matches, then the item statistics                                                                                                                                                                   |

## The timeline and the avoidable deaths

The timeline tab of the match page and the avoidable deaths of the review rest on the movement paths of the twelve players, which the archive keeps since format 2 (format 1 kept the tracked player's alone). Like the rest of the folder these modules are pure: they read a decoded archive and download nothing.

| Module                             | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `match-detail/player-paths.ts`     | `readPlayerPaths` reads the path of each player of an archive (a format-1 archive holds the tracked player's alone, and a path whose samples cannot be read, or a field of which, or of its player, has the wrong type, is left out on its own; `null` when the match has no paths at all, and an error only when `match_paths` itself is not what is expected); `positionAt` gives where a player was at a second of the match, `null` when they were dead or the path does not reach it. The sample index of a path is not always the game second, as some paths run ahead of the game clock: the shift is measured at each death of the player the path belongs to, and corrected in between |
| `match-detail/tracked-deaths.ts`   | `readTrackedDeaths`, above: the deaths the judgement starts from                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `analysis/avoidable-deaths.ts`     | `judgeDeaths` counts who was near the tracked player at each death (`nearbyAt`) and gives the verdict; `avoidableDeathCount` sums the avoidable ones up. A death is **avoidable** when no ally was near and at least `AVOIDABLE_MIN_ENEMIES` enemies were, an enemy killer always counted among them; any other death an enemy hero killed them in is balanced. A death with no enemy hero killer (troopers, the environment, a teammate, the player themselves) has no verdict. When the positions of the other players are not known (a format-1 archive, or a path that cannot be read), no death is judged, and the count is unknown (`null`), never `0`                                    |
| `analysis/review/review-values.ts` | Stores the count as the standalone key `avoidable_deaths`, written only when both the deaths and the positions are known                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `analysis/insights/thresholds.ts`  | `NEARBY_DISTANCE` (1500 map units, measured on the map from where the player died; a player exactly at it is near), `AVOIDABLE_MIN_ENEMIES` (2) and `AVOIDABLE_DEATHS_WEAK` (2 avoidable deaths in a match make it weak for that point)                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

The rule is an estimate: the paths only sample the players at intervals, so a player just outside the distance may still have weighed in the fight. `NEARBY_DISTANCE` and `AVOIDABLE_MIN_ENEMIES` change the stored count, so changing either needs a bump of `PROJECTION_VERSION`; `AVOIDABLE_DEATHS_WEAK` only acts when the review is shown, so it does not.

## Adding a metric

A metric is one number computed for every archived match, at the end of each synchronisation (or, as a fallback, when the page of a match not analysed yet is opened), and compared with the community and with the player's habits ([ADR 0004](../../docs/adr/0004-analysis-references.md)). To add a metric of the whole match:

1. Add its key to `MatchMetricKey` in `analysis/metric.ts`. If it is compared with a community percentile benchmark the app does not read yet, add that benchmark to `BenchmarkKey` and to `BENCHMARK_KEYS` (`deadlock-api/metric-benchmark.schema.ts`) too, and its percentiles to the development fixture of the API's answer (`src/adapters/dev/fixtures/analytics.fixture.ts`).
2. Write `analysis/metrics/<key>.metric.ts`, which exports a `MetricDefinition` (family, unit, which direction is better, group, display, how the habits are compared, the community source and `compute`), with its test `<key>.metric.test.ts` beside it. A metric returns `null` when the archive does not hold what it needs, never `0`. If it reads a field of the archive that the match context does not read yet, add the field to `analysis/match-context.ts` and to the synthetic match detail of the development fixture (`src/adapters/dev/fixtures/match-metadata.fixture.ts`), so that the development app and the tests have a value for it.
3. Add it to `MATCH_METRICS` in `analysis/registry.ts`, in the place of its family, and to the list of keys in `registry.test.ts`. A few tests pin the number of metrics and of stored values on purpose, so that a metric is never added by mistake: update the counts in `registry.test.ts`, `METRIC_VALUE_COUNT` in `src/services/projection.service.test.ts` and the number of rows in `src/services/analysis.service.test.ts`.
4. Add its name under `analysis.metric.<key>` in both catalogues (`src/ui/i18n/locales/{en,fr}/common.json`). The match page lists the metrics of the registry by family, and its tests take their counts from the registry; the stats tab of the review lists them the same way, under the same names.
5. Bump `PROJECTION_VERSION` in `analysis/registry.ts`: the matches stored with the old version are projected again from their archives at the next synchronisation, with no network access.

Bump it for a change to the damage values too, in `analysis/damage-sources.ts` or in the reader they come from, `analysis/damage-matrix.ts`, and for a change to the review values, in `analysis/review/review-values.ts` or in the readers they come from (`match-detail/tracked-deaths.ts`, `match-detail/tracked-items.ts`, `match-detail/scoreboard.ts`), and for a change to the avoidable deaths, in `analysis/avoidable-deaths.ts`, in the reader of the paths it works from (`match-detail/player-paths.ts`) or in `NEARBY_DISTANCE` and `AVOIDABLE_MIN_ENEMIES` (`analysis/insights/thresholds.ts`): they are stored with the metrics. Do not bump it for a change that leaves the projected values as they are (a text, the layout of the page). The metrics of a phase are a different case: `analysis/metrics/phase.metric.ts` builds all eleven from one table, the registry takes them from there, and the phase table names them. The thresholds that decide what counts as a strength or a weakness are in `analysis/insights/thresholds.ts`; those of the review are at the end of that file, and since they act on the stored values when the review is shown, changing one needs no new projection (but for `NEARBY_DISTANCE` and `AVOIDABLE_MIN_ENEMIES`, which change the stored count of avoidable deaths).
