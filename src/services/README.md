# `src/services` — use cases

A service implements the use cases of one area (settings, synchronisation, matches, hero names, the game's item and rank catalogues, the match detail archive, the linked Steam account, the match analysis, the match breakdown, the match timeline, the review of the last matches and the size limit of the archive folder). It orchestrates the pure logic of `core/` and the side effects behind `ports/`.

## Rules

- May import `core/`, `ports/` and other services (enforced by ESLint) — never an adapter: adapters are injected through the constructor.
- Validate everything read from a port before returning it: domain data with the schemas of `core/`, stored rows and cached payloads with the schema declared next to the code that reads them.
- Wrap failures of ports in `AppError` with the right `kind`; log meaningful events through the `Logger` port.
- One service per file, named `<name>.service.ts`, tested with the `adapters/dev` implementations.
- A repository, `<name>.repository.ts`, holds the SQL of one table (or, for `metrics.repository.ts`, of the two tables of the projections and their metrics; for `database-maintenance.repository.ts`, of the database file itself): both databases run it, it validates the rows it reads and wraps database failures in `AppError` of kind `storage`.
- `app-services.ts` lists the services exposed to the UI; `create-app-services.ts` builds them from the adapters, for the composition root and the tests alike. The UI reaches the Steam account through `AccountService` only: the sign-in, profile and data services are its parts and are not exposed. It reaches the analysis through `AnalysisService` only: the archive reader, the projection and the community data services work for it (the rank service and the projection work for the synchronisation too), and none is exposed. The damage and players tabs of a match come from `MatchBreakdownService`, which reads the stored projections, the archive and the hero, item and rank catalogues itself (so `GameAssetService` is not exposed either). The review page comes from `ReviewService`, which reads the stored projections, the cached community data, the item statistics of the tier above and the item and hero catalogues itself, and downloads that community data for the page; `BenchmarkService` and `ItemBenchmarkService` work for it and are not exposed. The timeline tab of a match comes from `MatchTimelineService`, which reads the archive, the match's detail state and the hero and item catalogues itself. The storage section of the settings comes from `StorageService`, exposed as it is; the detailed log and the log folder reach the UI as the `Diagnostics` port itself (it is a port with a handful of calls and no rule of its own, so no service stands between), set at start-up from the saved `debugLogging` setting. The updates come from `UpdateService`, exposed as it is: it holds the rules around the `UpdateGateway` port (one check per start, silent when it fails; the manual check of the settings, which reports its failure; one installation at a time, only when the player asks).
