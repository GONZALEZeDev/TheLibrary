# `src/services` — use cases

A service implements the use cases of one area (settings, synchronisation, matches, hero names, the game's item and rank catalogues, the match detail archive, the linked Steam account, the match analysis and the match breakdown). It orchestrates the pure logic of `core/` and the side effects behind `ports/`.

## Rules

- May import `core/`, `ports/` and other services (enforced by ESLint) — never an adapter: adapters are injected through the constructor.
- Validate everything read from a port before returning it: domain data with the schemas of `core/`, stored rows and cached payloads with the schema declared next to the code that reads them.
- Wrap failures of ports in `AppError` with the right `kind`; log meaningful events through the `Logger` port.
- One service per file, named `<name>.service.ts`, tested with the `adapters/dev` implementations.
- A repository, `<name>.repository.ts`, holds the SQL of one table (or, for `metrics.repository.ts`, of the two tables of the projections and their metrics; for `database-maintenance.repository.ts`, of the database file itself): both databases run it, it validates the rows it reads and wraps database failures in `AppError` of kind `storage`.
- `app-services.ts` lists the services exposed to the UI; `create-app-services.ts` builds them from the adapters, for the composition root and the tests alike. The UI reaches the Steam account through `AccountService` only: the sign-in, profile and data services are its parts and are not exposed. It reaches the analysis through `AnalysisService` only: the archive reader, the projection and the community data services work for it (the rank service and the projection work for the synchronisation too), and none is exposed. The damage and players tabs of a match come from `MatchBreakdownService`, which reads the stored projections, the archive and the hero, item and rank catalogues itself (so `GameAssetService` is not exposed either).

| `metrics.repository.ts`                                  | The projections and the values stored for the matches, metrics and damage sources alike (the `match_projections` and `match_metrics` tables)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `projection.service.ts`                                  | Projects archived matches into metric values and damage-source values (the damage of each source, the damage dealt while each shop item was owned, the unlock time of each ability), one projection at a time: the catch-up, every archived match without a projection of the current `PROJECTION_VERSION`, at the end of each synchronisation; and, as a fallback, a match and the earlier ones its habits are made of when its page is opened before it is analysed                                                                                                                                                        |

| `analysis.service.ts`, `analysis-view.ts`                | The analysis of a match page: the service reads what the synchronisation analysed and what it is compared with, and analyses a match not analysed yet when its page is opened, as a fallback (one at a time, in the exclusive section of the synchronisation); the view and its pure builders turn it into what the page shows                                                                                                                                                                                                                                                                                               |
| `analysis-subject.ts`                                    | Where a match stands before anything heavy is read for it: the one gate on the linked account, the detail status of the match and its projection (`not_analysed`, `pending`, `failed` or `projected`), shared by the analysis and the damage tab so that both tell the same states the same way; its first step, the linked account and an archived match (`archivedAccountOf`), is the gate of the players tab; reads the database only                                                                                                                                                                                     |
| `match-breakdown.service.ts`                             | The tabs of the match page besides its analysis: the damage and build tab (the damage by source compared with the player's habits, from the stored projections and the item and hero catalogues, and the final build, read from the archive) and the players tab (the twelve players with their heroes and ranks, read from the archive). A state says why a tab has nothing to show: for the damage tab, not analysed, pending, failed, archive unreadable or catalogue unavailable; for the players tab, not archived or archive unreadable (its catalogues only decorate it). A view never projects a match or changes it |
| `report-once.ts`                                         | The warning about a problem of a match (an archive a view cannot read), logged once per match and problem however often the page reads it; used by the analysis and the breakdown                                                                                                                                                                                                                                                                                                                                                                                                                                            |
